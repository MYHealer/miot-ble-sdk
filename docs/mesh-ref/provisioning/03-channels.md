# 03 通道与指令

## 通道分工

| UUID | 性质 | 承载内容 |
|---|---|---|
| `0x0010` | 控制 | 单字节指令 + 3 字节填充，用于流程控制与状态回报 |
| `0x0016` | 数据 | 多帧协议，承载证书、密钥包等大块数据 |
| `0x0019` | 数据 | 辅助，配网流程中观察到的数据量很少 |
| `0x001A` | 数据 | 辅助，同上 |
| `0x001B` | 只读属性 | 版本、规格，读请求返回 `Read Not Permitted` |
| `0x001C` | 明文命令 | 握手、能力查询、型号查询 |

`0x0010` 上的指令统一是 **4 字节**：`<cmd> 00 00 00`。后 3 字节在观察中恒为 0，推测预留。

`0x0016` 上的数据帧统一是 **`<seq> 00 <payload>`**，第 2 字节恒为 0，同样是预留位。

## 0x0010 指令表

按流程顺序：

| 指令 | 方向 | 触发时机 | 含义 |
|---|---|---|---|
| `A4 00 00 00` | App → 设备 | 握手完成后 | 请求设备上报证书 |
| `00 00 04 00` | 设备 → App | 收到 A4 后 | 前置通知：即将发 4 号包 |
| `A5 00 00 00` | App → 设备 | — | 版本 / 规格查询 |
| `40 00 00 00` | App → 设备 | auth 返回后 | 前置通知：即将下发服务器凭证 |
| `42 00 00 00` | 设备 → App | 服务器凭证验证失败 | 中止配网 |
| `43 00 00 00` | App → 设备 | bind 通过后 | 前置通知：即将下发配网数据 |
| `41 00 00 00` | 设备 → App | 配网数据处理完成 | **配网成功** |
| `47 00 00 00` | App → 设备 | auth 阶段 HTTP 失败 | 告知设备终止 |
| `49 00 00 00` | App → 设备 | bind 阶段服务器拒绝 | 告知设备终止 |

`40` / `43` 这两个"前置通知"的作用是给设备一个准备窗口 —— 收到通知后设备知道接下来要走 `0x0016` 收一个大包。

## 0x001C 明文命令表

这个通道不上加密，一问一答，用于握手阶段：

| 请求 | 响应 | 说明 |
|---|---|---|
| `00` | `00 02 03 08` | 协议版本查询。响应 4 字节为支持的能力位图 |
| `08 01 00` | `hello` | 存活探测，无业务副作用 |
| `03` | `03 07` + `MHCB12G` | 模组型号查询，返回长度 + ASCII 字符串 |

`08 01 00` 的响应是固定的 5 字节 ASCII `hello`。这个探测很有用：

- 不改变任何内部状态
- 响应快（毫秒级）
- 可以用来判断链路是否还活着

但它**不能延长设备对连接的生命周期管理**，见 [05 实测观察](05-observations.md)。

## 0x0016 多帧协议

已经在 [02 配网时序](02-provisioning.md#多帧传输协议0x0016) 里写过格式，这里补充实现层面的要点。

### 帧结构

```
偏移 0    seq        从 1 开始，每帧 +1
偏移 1    0x00       固定
偏移 2..   payload    最多 18 字节
```

最后一帧的 payload 可以不足 18 字节，接收方靠 START 里的帧数判断何时收完。

### START 帧

```
00 00 00 <pkg> <n> 00
         │      │
         │      └─ 后续数据帧数量（不是字节数）
         └──────── 包编号（1/3/4/7/8/9）
```

### 握手序列

```
发送方                     接收方
  |── START (pkg,n) ────────>|
  |<────────── ACK 00 00 01 01|
  |── 数据帧 seq=1 ──────────>|
  |── 数据帧 seq=2 ──────────>|
  |        ...               |
  |── 数据帧 seq=n ──────────>|
  |<────────── ACK 00 00 01 00|
```

### 实现注意

1. **串行化**。BLE 同一连接同一时刻只允许一个 GATT 过程。写帧必须等上一次写完成回调，否则 `EBUSY` 且丢帧。丢一帧整包就废，对端会一直等。
2. **帧间隔**。实测设备侧推送间隔 25–30ms。仿真时低于 20ms 容易触发对端缓冲溢出。
3. **MTU 影响**。MTU 从默认 23 协商到 247 后，单帧仍是 18 字节 payload —— 说明 18 是协议层固定值，不随 MTU 变化。
4. **超时**。整包传输超过约 15 秒未完成，App 侧会放弃并断开，表现为 `-7`。

## 已配网状态

设备配网完成后 **GATT 服务关闭**，上述所有通道都不可用。此时设备只响应 mesh 广播，控制必须经过网关。

这意味着：

- 无法在已入网设备上重复观察配网流程
- 无法通过 GATT 向已入网设备发指令
- 恢复出厂是唯一回到配网态的方式
