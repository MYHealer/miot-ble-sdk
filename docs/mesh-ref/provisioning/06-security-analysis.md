# 06 安全设计分析

这一节分析这套配网机制的安全性从哪来、边界在哪、以及为什么"通过空口获取设备私钥"在原理上不成立。

## 一、签名是单向的

设备私钥只在一个地方被使用：**对挑战做 ECDSA 签名**。

```
私钥 (32B)  ──┐
              ├──> ECDSA-P256 签名运算 ──> 签名 (r‖s, 64B)  ──> 空口
挑战 (64B)  ──┘
```

这个运算有两个性质决定了安全性：

1. **不可逆**。从签名和挑战反推私钥，等价于解椭圆曲线离散对数问题，P-256 下没有可行算法。
2. **私钥不出芯片**。签名运算在芯片内部完成，私钥只作为运算输入被读取，从不写入任何输出缓冲。所以无论监听 UART、SPI、还是 BLE 空口，看到的都只有签名。

这也是所有 TPM / Secure Element / 安全启动方案的共同设计前提。

## 二、私钥可能存放的三个位置

要拿到私钥，只能物理访问芯片。而"物理访问能不能拿到"取决于它存在哪：

| 位置 | 可读性 | 说明 |
|---|---|---|
| 明文 flash | ✅ 直接读 | 低成本方案常见，但会被轻易提取 |
| 加密 flash（key 在 OTP） | ⚠️ 需要先拿到 OTP 里的 key | 部分 Telink 方案支持 |
| 独立安全元件 / OTP 保护区 | ❌ 不可读 | 只能调用签名接口，无法导出 |

行业趋势是往第三类走。对米家这类走量的消费级设备，前两类更常见 —— 但这只是概率判断，不构成结论。

**关键**：无论属于哪一类，"空口"这条路都拿不到，必须有物理接触。

## 三、"私钥由 MAC / PIN 派生"假设的证伪

一个常见的猜测是：私钥不是随机的，而是用设备公开信息（MAC、产品 ID、PIN、SN）经某种算法派生出来的。如果成立，任何人都能算出任意设备的私钥。

**验证方法**：如果私钥是确定性派生的，那么用公开信息 + 已知派生算法算出的私钥，其对应公钥必然等于证书里那把。所以穷举所有合理组合，比对公钥即可 —— 不需要知道算法，只需要验证结果。

**实验**（`tools/derive_test.py`）：

| 维度 | 覆盖 |
|---|---|
| 种子 | MAC（大端 / 小端 / ASCII）、设备信息段、厂商证书 ID、公钥本身、两两拼接、PIN / SN 拼接 |
| 派生 | SHA-256、SHA-512 截断、双哈希、HMAC-SHA256、前缀 0x00/0x01、常见常量（mijia / miio / xiaomi / miot / mible / mesh 等） |
| 直接取值 | 种子前 32 字节 / 后 32 字节 / 整体当标量 |

**结果**：1190 个候选私钥，0 命中。

**结论**：私钥不是由公开信息派生的，是产线生成的真随机值。这也符合行业标准做法 —— 派生密钥一旦算法泄露就是全网沦陷，而随机密钥不存在这个风险。

顺带澄清一个概念错误：**米家 BLE Mesh 配网没有 PIN 码**。PIN 配网（WPS / SoftAP）是 WiFi 设备的做法。BLE Mesh 走的是证书 + 挑战签名，没有"输入 PIN 换取密钥"这个环节。

## 四、服务器校验的真实边界

实测发现服务器的校验分两层，而且两层强度不一样：

| 阶段 | 校验内容 | 严格程度 |
|---|---|---|
| `auth` | 证书链是否由米家根签发 | 只看证书，不比对连接 MAC、不比对 mesh 公钥 |
| `bind` | `pkg4` 是否由证书对应私钥签出 | 必须通过，否则拒绝 |

`auth` 阶段比较宽松，`bind` 才是真正的关口。这个设计是合理的：

- `auth` 只是建立会话，还没到"确认设备身份"那一步
- `bind` 用一次性挑战验证"对面确实持有私钥"，这才是身份证明

**所以"绕过 auth"没有意义**。即使让 `auth` 通过（用真证书），`bind` 仍然要求用证书私钥对服务器随机挑战签名。而私钥在芯片里。

这也解释了一个观察到的现象：把 `pkg3` 里的 mesh 公钥换成自己的，`auth` 过了、`bind` 照样失败 —— 因为签名验证用的是证书公钥，换 mesh 公钥不影响它。

## 五、为什么这套设计足够

从攻击者视角看，要伪造一台设备，需要突破：

1. 证书链验证（`auth`）
2. 一次性挑战签名（`bind`）—— 需要私钥
3. 配网数据的解密 —— 需要 ECDH 会话密钥，而会话密钥由设备私钥参与派生

第 2 步是核心。只要私钥不出芯片，前两步后面的所有环节都无从谈起。这就是"安全边界"的定义：**不是让攻击变难，而是让某一类攻击在数学上不可能**。

## 六、结论：要让自己的硬件接入米家，正确的路是什么

如果目标是"我的硬件出现在米家、能被 App 和小爱控制"，其实不需要碰上面这些：

| 方案 | 是否需要私钥 | 可持续性 |
|---|---|---|
| 伪造已有设备的身份 | ✅ 需要（不可能获得） | ❌ 违反协议、随时失效 |
| **官方 BLE Mesh 模组** | ❌ 不需要，模组自带 | ✅ 官方维护、支持 OTA |
| 小米 IoT 开发者平台注册产品 | ❌ 不需要，走正规审核 | ✅ 完全合规 |

官方模组（如 MHCB 系列）的工作方式：

- 模组出厂时已烧录合法证书与私钥，在产线上完成
- 配网、mesh 入网、报文加解密全部在模组内部完成
- 开发者拿到的接口是 **UART 上的业务指令**：`get_down` 取下行命令、回 `ok`、上报属性变化
- 技能不涉及任何密钥操作

这意味着：**绝大多数"我要做一台米家设备"的需求，8–10 元的模组就能解决**，而且比任何自研方案都稳。

## 七、关于本文的边界

本文描述协议行为与安全设计，目的是理解互操作性。以下内容不在本文范围：

- 任何绕过设备绑定校验的方法
- 任何设备身份材料（证书、私钥、真实 MAC）
- 任何针对具体产品的攻击步骤

如果你在评估自己产品的安全性，上面"服务器校验的真实边界"那一节是可以直接拿去做威胁建模的：**假设你的设备私钥可能泄露，你的系统还能撑住吗？**
