# 05 实测观察

这一节记录在真机上反复实测得到的、文档里查不到的行为特征。有些直接决定了方案的可行性。

## 一、单条 BLE 连接有约 20 秒硬性寿命

**现象**：设备被连接后，无论是否有数据往来，都会在约 **20.0 秒** 后主动断开，断开原因码 `0x213`（`0x13` = Remote User Terminated）。

实测序列（三次连续连接）：

| 连接建立 | 被断开 | 存活 |
|---|---|---|
| 1.1s | 21.0s | 19.9s |
| 21.5s | 41.4s | 19.9s |
| 41.6s | 61.4s | 19.8s |

精度非常高，每次都是 19.8–20.0 秒。

**排除项**：

| 假设 | 实验 | 结果 |
|---|---|---|
| 连接间隔太激进导致对端不适 | 请求 7.5–15ms 参数 | 仍 20.0s 断开 |
| 同上 | 不请求自定义参数，用默认 30–50ms | 仍 20.0s 断开 |
| 空闲超时（无数据就断） | 持续发 `08 01 00` 探测，每 3s 一次 | 探测有应答，仍 20.0s 断开 |
| 读操作能续命 | 每 4s 读一次 `0x001B` | 返回 `Read Not Permitted`，断开时间不变 |

**结论**：这是设备固件里的单连接生命周期上限，不是协商参数、也不是空闲检测。改连接参数无效。

**影响**：

- 任何"先连上等着"的方案都会在等待期间白白消耗窗口
- 配网流程从握手到 `pkg9` 需要 15–25 秒，正好卡在边缘
- 如果链路的 20 秒窗口从"连接建立"开始算，而配网要 20 秒后才开始，必然断在传输中途
- 断在传输中途的典型表现就是 `-28`

**可行的应对思路**（研究场景）：让链路在真正需要时才开始计时。这需要外部手段控制建链时机，而不是让设备一直挂着。

## 二、断链后短时间内拒绝重连

设备被断开后，会有一小段时间不再接受连接（连接请求超时，`status=13`）。反复快速重连会让这个窗口变长，最后需要断电重启才能恢复。

实测：连续 5 次快速重连后，后续所有连接都超时，只能给设备断电。

## 三、被连接后立即停止广播

设备一旦被任何中心设备连接，**广播立即停止**。断开后不会马上恢复，取决于它自己的状态机。

这带来一个实践问题：如果需要在附近用扫描工具观察设备，它必须在未被连接的状态。

## 四、auth 阶段不校验 MAC

用设备 A 的证书、但连接建立时的 MAC 是设备 B 的，`auth` 阶段照样通过。

说明：**服务器在校验证书时只看证书内容，不比对这次连接的 MAC**。

`bind` 阶段是否校验 MAC，未做隔离实验（因为 `bind` 还卡在签名这一步），但从协议设计看，服务器此时已经拿到了 `did`，理论上可以做一致性校验。

## 五、服务器不绑定 mesh 公钥

用**真实的设备证书** + **自己生成的 mesh 公钥**（替换 `pkg3` 里那 64 字节），`auth` 阶段照样通过。

说明：服务器只验证"证书链是否可信"，不校验"证书里的公钥和 `pkg3` 里的 mesh 公钥是否一致"。

但这个口子没有实际利用价值 —— 因为 `bind` 阶段的签名验证用的是**证书里那把公钥**，换掉 `pkg3` 里的公钥改变不了"必须用证书私钥签名"这个事实。

## 六、挑战一次性，签名不可重放

同一台设备连续配网三次，抓到的 `pkg4` 各不相同。把历史 `pkg4` 原样提交，服务器拒绝（`-40`）。

原因：`pkg8` 里包含服务器生成的随机量，`pkg4` 是对这个随机量的签名，所以每次不同。

## 七、多帧传输的实际耗时

451 字节证书分 26 帧：

| 指标 | 实测 |
|---|---|
| 帧间间隔（设备侧） | 25–30ms |
| 整包耗时 | 约 0.7 秒 |
| 单帧 payload | 18 字节（固定，不随 MTU 变） |

MTU 从 23 协商到 247 之后，单帧 payload 仍是 18 字节 —— 说明分片大小是协议常量，不是按 MTU 计算的。

## 八、配网完成后 GATT 完全关闭

`41 00 00 00` 之后约 1.4 秒，设备断开连接并关闭 GATT 服务。之后：

- 无法再连接（连接请求超时）
- 无法读任何特征值
- 只能通过 mesh 广播通信

这一条决定了：**已配网设备无法用于重复观察配网流程**，每次实验都要恢复出厂。

## 九、Android HCI 日志的实际限制

想在系统层抓 BLE 数据时踩到的坑：

| 尝试 | 结果 |
|---|---|
| `settings put global bluetooth_hci_log 1` | 需要**重启手机**才生效 |
| 重启后抓到的日志 | 只有 HCI command / event，**没有 ACL 数据** |
| `setprop persist.bluetooth.btsnooplogmode full` | 被 SELinux 拒绝 |
| 开发者选项里的"启用 HCI 信息收集日志" | 同上，filtered 模式 |

结论：非 root 的 Android 设备拿不到完整的 GATT 层数据。要抓完整链路，只能在链路中间做（例如在中心设备侧记录），或者用专门的 BLE sniffer 硬件。

## 十、连接参数协商

| 参数 | 默认 | 协商后 |
|---|---|---|
| MTU | 23 | 247 |
| 连接间隔 | 30–50ms | 可协商到 7.5ms |
| 从机延迟 | 0 | 0 |
| 超时 | 通常 4s | 可设 8s |

协商到 7.5ms 不会改变设备的 20 秒行为，但能显著降低多帧传输的总耗时（帧间等待变短）。在 20 秒窗口内，这是唯一能争取到的余量。
