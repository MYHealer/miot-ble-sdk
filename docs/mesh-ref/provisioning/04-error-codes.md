# 04 错误码

配网失败时 App 会弹一个负数错误码。这些码和 BLE 层的 GATT 错误、设备侧指令码是三套完全不同的东西，容易混淆。

## 三套码的层次

```
App 弹窗错误码（-7 / -28 / -39 / -40 …）
    ↑ App 层根据失败阶段归类
BLE / GATT 层错误（0x02 Read Not Permitted / 0x85 等）
    ↑ 传输层
设备侧 4 字节指令码（42 / 41 / 47 / 49 …）
    ↑ 设备固件行为
```

## App 侧错误码

| 码 | 语义 | 常见成因 |
|---|---|---|
| `-7` | 操作超时 | 设备无响应、链路中断、某帧丢失后对端一直等 |
| `-17` | 设备已注册 | 试图配网一台已入网的设备 |
| `-28` | 数据传输过程中失败 | 传输途中链路断开（见 05 文档的 20 秒现象） |
| `-39` | auth 阶段失败 | 服务器拒绝设备证书（证书链不可信 / 内容不符） |
| `-40` | bind 阶段失败 | 服务器拒绝设备签名 |
| `-41` | 设备拒绝 | 设备侧主动中止 |
| `-46` | 找不到设备 | 广播已停止 / 距离过远 |

### 定位方法

按时间顺序推断失败点比看码更快：

| 现象 | 失败位置 |
|---|---|
| 几秒内就报 `-39` | 证书上传后立刻被拒 → 证书本身有问题 |
| 传输证书过程中报 `-28` | 链路在传帧途中断了 |
| 走完服务器凭证下发后报 `-40` | 设备签名没通过服务器验证 |
| 全程无反应，15 秒后 `-7` | 设备根本没收到帧，或收到但没回 |

## 设备侧指令码

这些是 `0x0010` 上的 4 字节指令，反映设备固件的判断：

| 码 | 方向 | 含义 |
|---|---|---|
| `41 00 00 00` | 设备 → App | 配网数据处理完成（成功） |
| `42 00 00 00` | 设备 → App | 服务器凭证验证失败，中止 |
| `47 00 00 00` | App → 设备 | 通知设备：auth 阶段失败 |
| `49 00 00 00` | App → 设备 | 通知设备：bind 阶段失败 |

注意方向：`42` 是**设备主动发**的中止信号，`47` / `49` 是 **App 发给设备**的通知。收到 `42` 说明设备本地就没通过验证，这时候 App 还没走到服务器那一步。

一个容易误判的点：**`42` 不是成功码**。它长得像"状态 42"，实际是终止帧。真正的成功信号是 `41`。

## GATT 层错误

| 错误 | 值 | 场景 |
|---|---|---|
| `Read Not Permitted` | 0x02 | 读 `0x001B` 等只读属性时被拒 |
| `Insufficient Authentication` | 0x05 | 未完成绑定就访问受保护特征值 |
| `Insufficient Encryption` | 0x0F | 链路未加密 |
| `EBUSY`（主机栈） | NimBLE 内部 | 上一个 GATT 过程未完成就发起新操作 |

`EBUSY` 不是设备返回的，是本地主机栈拒绝。多帧推送时如果不做串行化，会看到大量这个错误，同时伴随丢帧。

## 排查顺序建议

1. **看有没有 `41`** —— 有就是成功，其它码可忽略
2. **看 `42` 有没有出现** —— 有就是设备侧验服务器失败，问题在凭证下发环节
3. **看 `47` / `49`** —— 有就是服务器拒绝，问题在证书或签名
4. **看 GATT 层断链** —— reason `0x213`（Remote User Terminated）说明对端主动断开
5. **都没有，只有超时** —— 检查帧有没有真的送达（逐帧打印比对）

## 关于 `-28` 的说明

`-28` 在官方文档里的描述是"数据传输过程中，数据发送失败"。实测它最常见的成因不是发送失败，而是**发送成功但对端在传输途中断开**，导致后续帧全部落空。

如果遇到 `-28`，先确认对端有没有自己的连接生命周期管理，再看链路参数。
